## 2. 阶段一：棋盘逻辑 board.gzg（15:45–15:55）

约 230 行。写完后用一个临时脚本 import 它冒烟测试：`slide_row([2,2,2,2])` 得 `[[4, 4, 0, 0], 8]`，`Game.step/undo` 正常。
**这一阶段零报错**——文档的速览和 15 条规则足够写出这种纯逻辑代码。

## 5. 阶段四：AI ai.gzg 与性能调优（16:10–16:20）

**第一版**：expectimax（玩家节点取 4 个方向最大值，机会节点对每个空格按 0.9/0.1 放 2/4 求期望），
叶子评估按“线”（4 行 + 4 列）计算 log2 等级上的空格数、可合并数、单调性惩罚、大数惩罚，每条线的分数用字典缓存。
`choose_depth`：空格 ≥ 6 深度 2，否则 3。约 150 行，**语法和运行都没有报错**，函数 `chance_node` 调用后面才定义的 `max_node`（互相递归）也没问题。

**问题 P1 [性能]**：seed 1 跑 300 秒超时，只走了 200 步（1.3 秒/步）。不算报错，但这是本阶段唯一的大问题。

用 `clock()` 写了 `_prof.gzg` 做微基准（每次调用的耗时）：

| 操作 | 微秒 |
|---|---|
| `move_cells`（含 copy、取行、查行缓存） | 3.81 |
| `evaluate`（8 条线、查缓存） | 2.22 |
| `empty_indices` | 0.78 |
| 拼字符串键 `"{a},{b},{c},{d}"` | 0.17 |
| 整数键 `((a*31+b)*31+c)*31+d` | 0.04 |
| `copy(16 元素数组)` | 0.49 |
| 字典按整数键 `get` | 0.02 |

单次操作都不慢，慢在节点数：深度 3 在空格多的时候会展开几十万个节点。改法：

1. 概率剪枝阈值 0.0001 → 0.001，深度 3 只在空格 < 4 时用 → seed 1 用 590 秒到 2000 步，最大块 4096（约 0.3 秒/步）。
2. 加置换表 `TRANS`（同一次 `best_move` 内，键 = `cells.join(",") + "|" + 深度`）→ 2000 步 192 秒（约 0.1 秒/步），走法和之前一模一样（说明缓存没改变结果）。
   在 `best_move` 里写 `TRANS = {}` 给顶层变量重新赋值也可以——文档只说函数里 `let` 是局部，没说对顶层变量赋值是改全局，试了才知道。
3. 空格 ≥ 8 时用深度 1 → seed 1 在 570 秒时到 4400 步、最大块 8192，但一局要 10 分钟左右。

AI 已经远超“稳定 512”的要求，所以我没有继续优化（比如把行编码成整数、预计算 65536 种行），
代价是 `--auto --fast` 一局要几分钟，README 里写明了。

### E1 [语法] 按 Python 习惯写了 `a if c else b`

恢复会话后第一次运行 `main.gzg --auto --fast --seed 42`：

```
apps/game2048/main.gzg:95:42: 语法错误: 实参列表缺少 ')'（在 'if' 处）
    95 |         print("\e[1m2048\e[0m  (h 帮助)" if false else (color ? "\e[1m== 2048 ==\e[0m  输入 h 查看帮助" : "== 2048 ==  输入 h 查看帮助"))
       |                                          ^
apps/game2048/main.gzg:95:51: 语法错误: 这里需要 '{'（在 'else' 处）
    95 |         print("\e[1m2048\e[0m  (h 帮助)" if false else (color ? "\e[1m== 2048 ==\e[0m  输入 h 查看帮助" : "== 2048 ==  输入 h 查看帮助"))
       |                                                   ^
apps/game2048/main.gzg:232:5: 语法错误: 结构体成员之间用换行或 ',' 分隔（在 '(' 处）
   232 | main()
       |     ^
```

- 为什么这样写：写标题行时先想写一个固定标题，后来想按 `color` 区分，就在原表达式上套了一层，结果混用了 Python 的 `x if c else y` 和 GZG 的 `c ? x : y`。这是习惯性错误，GZG 文档的运算符速查里明确只有 `c ? x : y`。
- 怎么改：整行换成 `print(color ? "..." : "...")`。
- 文档有没有帮上：报错的列号准确指向 `if`，看一眼就知道问题在哪。但信息“实参列表缺少 ')'”并没有说 GZG 没有 Python 式条件表达式；SKILL.md 承诺的“你是不是想写 'xxx'？”这次没有出现。第三条（232 行）是解析器没能从错误中恢复带出来的连锁错误，`main()` 被当成了结构体成员，第一次看会让人以为文件末尾也有问题。
- 统计：1 个根因，解释器报了 3 条，计为 1 次语法报错。

### 解释器 bug：程序卡住不退出（不是我的代码问题）

上面这个错误第一次出现时（中断之前），旧版 `build/stable/gzg.exe` 打完报错**不退出**，进程一直挂着（任务管理器里还剩一个 gzg.exe，PID 65912，被我 `taskkill` 掉）。

### 只能靠试验确认的东西（文档里没有）

1. `import` 的全部语义：只支持 `import "x.gzg"`；路径相对导入方文件；导入的名字进全局；不支持 `as`；扩展名不能省；重复导入不报错。
2. 文件函数的路径相对当前工作目录（和 import 不一致）；没有 `__file__` 或其他拿脚本路径的方法。
3. 结构体字段默认值 `= []` 每个实例各一份。
4. 函数内 `x += 1`、`x = {}` 会直接修改顶层变量，不需要 `global`。
5. `seed()` 同时影响 `randint` 和 `random()`；`float("inf")` 可用。
6. 性能量级：100 万次函数调用约 0.015 秒；字符串键的开销约是整数键的 4 倍。

### 缺失或误导之处与改进建议

1. **缺 `import`**（最严重）：任务要求拆文件，三份文档却一个字都没提。建议写明语法、路径基准、命名空间、是否只执行一次。
2. **缺路径和全局变量规则**：写明文件 IO 相对 cwd、import 相对脚本，提供（或明确说明没有）拿脚本目录的方法；写明函数内对顶层变量赋值就是修改全局。
3. **条件表达式**：明确写出“没有 `a if c else b`，只有 `c ? a : b`”，报错时给出“你是不是想写”的提示。
4. **缺性能提示**：写搜索类程序最需要知道哪些操作贵（拼字符串、`copy`、字典键类型）。
5. 错误恢复：E1 的连带报错（`main()` 被当成结构体成员）容易误导，可以在第一条错误后抑制同一结构体内的后续报错。
